# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Lexi is a Chrome Manifest V3 extension: a once-a-day AI-picked word shown in a dismissible, collapsible corner widget, plus the ability to save words (by highlighting them on any page, or typing them in) and review them in a side panel with search and a lightweight quiz. Word explanations and the daily word pick come directly from a user-chosen LLM provider (Anthropic, Google Gemini, or Groq), called client-side with a user-supplied API key for that provider (no backend).

## Commands

```bash
npm test               # run the full Vitest suite once
npm run test:watch     # Vitest in watch mode
npm test -- tests/lib/storage.test.ts   # run a single test file
npm run build          # bundle with esbuild into dist/ (also copies manifest.json + HTML pages)
```

There is no lint script configured. `tsconfig.json` has `noEmit: true` — type checking happens through the editor/`tsc --noEmit`, not as a build step; `npm run build` only bundles with esbuild and does not type-check.

To manually verify the extension end to end: `npm run build`, then load the `dist/` folder as an unpacked extension via `chrome://extensions` (Developer mode → Load unpacked), set an API key on the options page, and exercise the widget/highlight-to-save/side-panel (library, search, add a word) flows.

## Architecture

**Split between tested logic and untested glue.** All business logic (storage, prompt building/parsing, daily-trigger decisions, search, quiz ordering) lives in dependency-injected modules under `src/lib`, `src/sidepanel`, and `src/content` (excluding `content/index.ts` and `content/selection.ts`), and is unit-tested with Vitest against a fake storage area — never real `chrome.*` APIs. The entry points (`src/background/index.ts`, `src/content/index.ts`, `src/content/selection.ts`, `src/sidepanel/index.ts`, `src/options/index.ts`) are thin wiring that call the tested functions with real `chrome.storage`/`chrome.contextMenus`/`chrome.tabs`/`chrome.scripting`/`chrome.sidePanel`, and are deliberately *not* unit tested — there's no good way to test MV3 service worker event wiring without just testing mocks (the widget's own render function is the exception — `renderWidget` is a pure DOM-building function taking a ShadowRoot, data, and handlers, so it's tested directly rather than through the page/mount glue). Verify entry-point changes manually via the unpacked-extension flow above. When adding a feature, put the decision logic in `src/lib` (or a `src/sidepanel`/`src/content` helper) with a DI-friendly signature and a test, then wire it into the relevant entry point last.

**No native popup.** The toolbar icon opens a Chrome **side panel** (`chrome.sidePanel`, declared in `manifest.json` under `side_panel.default_path`), not `action.default_popup` — `src/background/index.ts` calls `chrome.sidePanel.setPanelBehavior({ openPanelOnActionClick: true })` so clicking the icon opens it directly. The side panel reserves real layout space next to the page (as opposed to a transient floating popup), matching the product's "side panel that pushes the page" requirement. `src/sidepanel/index.ts` is a small hand-rolled single-page app (no framework, consistent with the rest of the codebase) that switches between `library` / `search` / `save` views by re-rendering into a single `#app` container (search replaced the old "All saved words" list; the quiz view is hidden for now but `src/sidepanel/quiz.ts` is kept) — there's no router or separate HTML page per view. Because words can also be saved from the highlight-to-save popover or the widget (different execution contexts), it listens for `chrome.storage.onChanged` on the `lexi.words` key and re-renders while on `library`/`search` so a save from elsewhere shows up without the user having to navigate away and back; it skips this on `save` so it doesn't clobber in-progress input. The `save` view also does a debounced (500ms, plus on blur) live preview of the word/pronunciation/meaning/example as the user types, reusing the already-saved record's cached detail instead of re-calling the model if the word is already in the library, and reusing its own fetched preview (rather than calling `explainWord` a second time) when the user then clicks "Add to my library".

**Two-tier storage**, wrapped by a common `StorageArea` interface (`src/lib/storage.ts`) so `chrome.storage.sync`/`chrome.storage.local` and the test fake (`tests/mocks/fakeStorageArea.ts`) are interchangeable:
- `chrome.storage.sync` — compact word records (`src/lib/storage.ts`, key `lexi.words`) and the shared "today's word" (`src/lib/dailyWord.ts`, key `lexi.todayWord`), so a user's devices agree on the daily word. Kept small to stay under Chrome's sync quota.
- `chrome.storage.local` — the full AI-generated meaning/example cache (`src/lib/cache.ts`, key `lexi.cache`), the per-device "widget already shown today" flag (`src/lib/dailyWord.ts`, key `lexi.lastShownDate`), and the API key (`src/lib/apiKey.ts`, key `lexi.apiKey`) — local/local-only so the key never syncs across devices.

Word records are deduplicated case-insensitively by `word` in `storage.ts`; the same rule is reused wherever a word is looked up (`addWord`, `wordOfDayService`).

**Orchestration layer** (`src/lib/wordOfDayService.ts`, `src/lib/addWord.ts`) composes the lower-level stores and the model client:
- `ensureTodayWord` — no-ops if today's word is already cached (by date), otherwise asks Claude for a word (excluding previously-used *daily* words only, not manually-added ones), explains it, and caches the detail plus a `TodayWordRecord` (word, date, topic) - it does **not** add the word to the library. `saveTodayWord` is what actually writes it to `wordStore` (`source: "daily"`, using only what's already cached - no model call), called from the widget's "Add to my library" button and the side panel's today's-word banner (below); both are idempotent since `wordStore.saveWord` no-ops on an existing word. One consequence: a daily word that's shown but never saved doesn't count toward the "previously shown daily words" exclusion above, since that history is read from `wordStore`, not from what's merely been shown.
- `shouldInjectWidget` / `markWidgetShown` — wrap the pure `shouldShowWidgetToday` (`src/lib/trigger.ts`) date comparison with the local last-shown-date store.
- `addWord` — shared by the context-menu handler, the highlight-to-save popover, and the side panel's manual-add form; returns the existing record without calling Claude again if the word is already saved.

**Multi-provider model client.** `src/lib/prompts.ts` holds the provider-agnostic, directly-unit-testable prompt-building/response-parsing functions (`buildExplainPrompt`, `parseExplainResponse`, `buildWordOfDayPrompt`, `parseWordOfDayResponse`) — both prompts request strict JSON-only responses so parsing can throw on malformed output. A word explanation (`WordExplanation`, mirrored in storage as `FullWordDetail`) carries `meaning`, `example`, `pronunciation` (IPA), and `partOfSpeech`; `parseExplainResponse` defaults the latter two to `""` if a model omits them, since not every provider/prompt combination reliably returns them. `src/lib/providers/{anthropic,gemini,groq}.ts` each export one `call*(apiKey, prompt): Promise<string>` function that knows that provider's endpoint, auth style (header vs. query param), request body shape, and response shape — this is the only part of the codebase that differs per provider. `src/lib/modelClient.ts`'s `createModelClient(provider, apiKey)` picks the right `call*` function and wraps it with the shared prompt builders/parsers to produce a `ModelClient` (`explainWord`/`pickWordOfDay`), which is what the rest of the app (`addWord`, `wordOfDayService`) depends on — they never know which provider is in use. Each provider file has a `MODEL` constant with a comment to double-check it's still current before shipping. The user's choice of provider + key is stored together as one `ApiKeySettings` object (`src/lib/apiKey.ts`, key `lexi.apiKey`) and set via a provider `<select>` on the options page (`src/options/`); `isPlausibleApiKey(provider, key)` does a light per-provider prefix/length sanity check, not real validation.

**Background service worker** (`src/background/index.ts`) is the only place that reacts to `chrome.*` events: it creates the "Add to Lexi" context menu on install, sets the side-panel-on-click behavior, calls `addWord` on a context-menu selection, and on tab activation / window focus change calls `maybeShowWidget`, which chains `shouldInjectWidget` → `ensureTodayWord` → `chrome.scripting.executeScript` (injecting `content.js`) → `markWidgetShown`. That widget content script is injected programmatically rather than declared in the manifest, so it only ever runs when the background worker decides to show the widget, not on every page load — unlike `selection.js` (below), which *is* declared in the manifest and runs on every page.

**Content script widget** (`src/content/widget.ts`) renders into a Shadow DOM to avoid CSS collisions with the host page, and always sets rendered word/pronunciation/part-of-speech/meaning/example via `.textContent` (never interpolated into `innerHTML`) so page content can't inject HTML into the widget. The body below the header uses a tiled dashed-line SVG background (`.ruled`) instead of per-section borders, matching the finalized "ruled paper" reference design. It's collapsible: clicking the minimize icon re-renders the same shadow root as a small pill showing just the word; clicking that pill re-expands it. Its "Save to library" button calls an injected `onSave` handler (`saveTodayWord` from `wordOfDayService.ts`, idempotent) and shows a disabled "Saving…"/"Saved to library" state, falling back to an inline error on failure — `renderWidget` stays a pure, DI-friendly, directly-tested function (ShadowRoot + data + handlers in, DOM out), with `mountWidget` as its thin untested wiring. `src/content/index.ts` (glue) reads what the background worker already wrote to storage, wires `onSave` to `saveTodayWord`, and mounts the widget — it makes no AI calls itself, and (unlike the highlight-to-save popover) doesn't need to message the background worker either, since `saveTodayWord` only touches `chrome.storage`, which isn't subject to the host page's CSP the way a content script's own `fetch()` is.

**Today's-word banner** (`renderTodayWordBanner` in `src/sidepanel/index.ts`) is the fallback for a widget closed without saving: a small card above the library list showing today's word (pronunciation, meaning, example, from the same detail cache the widget reads) with a compact "Add" button that calls `saveTodayWord`. `shouldShowTodayWordBanner` (`src/lib/trigger.ts`) gates it: it only shows once the widget has had its one shot for the day (`lastShownDate === today`, so it never appears alongside the widget itself) and only until the word is saved or the day turns over - both read through the same `todayWordStore`/`lastShownStore`/`wordStore` the widget and background use, so the banner, the widget, and a save from either always agree.

**Highlight-to-save content script** (`src/content/selection.ts`) is declared directly in `manifest.json`'s `content_scripts` (matches `<all_urls>`), so — unlike the on-demand widget script — it runs persistently on every page, listening for `mouseup`/selection events. When the user highlights a short run of text outside an editable element, it shows a small Shadow-DOM popover near the selection with an "Add to my library" button that calls the shared `addWord` flow directly (skipped entirely if no API key is set yet). This is the "save a word by highlighting it while browsing" flow, distinct from the existing right-click → "Add to Lexi" context-menu item, which still exists as an alternative entry point into the same `addWord` function.

**Quiz ordering** (`src/sidepanel/quiz.ts`) prioritizes never-seen words, then lowest known/seen ratio, over anything already mastered. It is currently not reachable from the UI (the Quiz me button was removed while the side panel was redesigned).

**Topics and search.** The explain prompt also asks the model for one `topic` from the fixed `TOPICS` list in `src/lib/prompts.ts` (unknown values become `Other`); `addWord` and `saveTodayWord` store it on the compact word record (`CompactWordRecord.topic`, optional - words saved before topics existed are grouped as `Other`). `src/sidepanel/search.ts` derives the filter chips (`topicChips`, one per topic present, biggest first, `Other` last) and does the searching (`searchWords`: chip narrows to a topic, the query then matches word, meaning or topic). `wordStore.getAllWords()` returns words in save order (oldest first, since `saveWord` appends); `search.ts`'s `newestFirst` reverses that once in `render()` (`src/sidepanel/index.ts`) so the library list and every search result show the most recently saved word first. In the Search view, All shows one flat list; selecting a chip shows that topic under a `Topic · N` title. The header's trash icon turns on select mode (`renderSearch`'s `selectMode`/`selectedWords` state, module-level like `searchQuery`/`searchTopic` so it survives a re-render mid-selection): rows show a checkbox in place of the chevron (`wordRow`'s optional `select` param), the header swaps to Cancel / a live "N selected" count / Select all, and a bottom drawer takes the footer's place - a short warning line and a "Delete from library (N)" button that calls `wordStore.deleteWords` (one read/write for the whole selection, so it fires a single storage change instead of one per word). In Add a word the button appears below the preview, only once a preview exists, and on success shows feedback in the button itself ("Added to my library", disabled) rather than a separate success line - matching the "Saving…"/"Saved to library" pattern already used by the widget's and highlight-to-save popover's own save buttons. The saved state is a light outline pill (`.primaryBtn.saved` in `src/sidepanel/index.html`: card-colour fill, thin green border, green text/checkmark) rather than a solid fill, matching the highlight-to-save popover's own saved button.

**Profile, onboarding and Settings.** The user's profile (`src/lib/profile.ts`, key `lexi.profile` in `chrome.storage.sync`) holds the linked Google account email, the name that titles the library ("Priya's Library"), the daily arrival time (24h `HH:MM`), a goal (`GOALS`; only "Learn industry jargon" asks a follow-up "Which industry?") and an `onboarded` flag. Three things consume it: (1) `maybeShowWidget` in the background worker injects `onboarding.js` (instead of the widget) on any http(s) tab until `onboarded`, and `onInstalled` (`reason === "install"`) shows it straight away (falling back to opening `welcome.html` when the active tab isn't scriptable); once onboarded, the widget is held back until `hasArrived(now, arrivalTime)`; (2) `ensureTodayWord` takes an optional `preference` sentence (`profilePreference`: goal + industry) that `buildWordOfDayPrompt` folds into the daily-word prompt - it only passes a second argument to `pickWordOfDay` when there is one; (3) the side panel's Settings view. The onboarding pop-up (`src/content/onboarding.ts`, entry `onboardingEntry.ts` -> `dist/onboarding.js`) is a 4-step centred dialog in a Shadow DOM: sign in, name, arrival time, goal. `renderOnboarding` is a pure, tested DOM function like `renderWidget`. Sign-in is `chrome.identity.getProfileUserInfo` (the Google account the *browser* is signed into - the manifest needs `identity` + `identity.email`); content scripts can't call it, so they message the background worker (`SIGN_IN_MESSAGE` in `messages.ts`). There is no real OAuth or backend account yet, so "Sign in"/"Sign out" only link or unlink that email, and a browser with no Google account simply continues without one. Settings (`src/sidepanel/settings.ts`, `renderSettings`, tested) edits the same four things (goal is a dropdown with the current goal on top, time is a dropdown, the industry field appears for the jargon goal) with Save changes and a tertiary Delete account (`deleteAccountData` in `src/lib/account.ts` clears the profile, library, today's word, cache and shown flag, then re-opens onboarding via `SHOW_ONBOARDING_MESSAGE`). The dropdown, goal picker and industry field live in `src/ui/controls.ts` and are shared by both; they and their CSS (`CONTROLS_CSS`, scoped under `.lx`) are the only place that markup is defined. The designs are the finalised boards in the "Lexi Onboarding & Settings" design canvas. **Logo:** the final mark is logo "B" (tilted red square stamp with a serif L). `src/lib/logo.ts` (`logoMarkSvg(size)`) inlines it, tile-less, in the onboarding header and the highlight popover's header (inline SVG so it renders under any page CSP; each call gets its own filter id). The toolbar/store icon is the same mark on its ivory tile, rendered to `icons/icon-{16,32,48,128}.png` (declared in `manifest.json`, copied to `dist/icons` by the build) from `assets/lexi-stamped-outline.svg` - Chrome manifest icons must be PNG, so re-render them if the artwork changes.
